## Contexte

Le propriétaire a demandé que les ingrédients communs soient ceux de l'administrateur (« plus de traitement particulier ») et que seuls ceux qu'il juge **de base** partent chez les futurs comptes. Le classement est fait et validé : 261 anciens communs, **151 de base, 110 spécifiques**. Ce ticket livre la **commande de passation** et ses données : elle pose le marqueur d'après le fichier, amorce les comptes actifs qui n'ont rien (le compte vide), contrôle les préconditions, passe les 261 au propriétaire, vérifie. C'est une **écriture sur la production** : tout se prouve avant (à blanc), pendant (empreintes, une transaction) et après (contrôles SQL).

## Spécification technique

**Phases** (`sans-commun.md` § 6) : 1 classer ; 2 amorcer ; 3 contrôler ; 4 passer ; 5 vérifier. **Préconditions** (relues dans la transaction de la phase 4, la commande dit laquelle manque et n'écrit rien) :

| | |
|---|---|
| P1 | le propriétaire est résolu par `IngredientCatalogOwner`, `ACTIF`, administrateur, protégé |
| P2 | aucune ligne (recette par auteur, liste et ingrédient de liste par propriétaire, choix du drive par `Shared`) d'un compte **autre que le propriétaire**, quel que soit son statut, ne référence un ingrédient sans créateur |
| P3 | tout compte `ACTIF` autre que le propriétaire est amorcé (`isAdopter`) et a au moins un ingrédient |
| P4 | `IngredientSeedingFeature::isEnabled()` est vrai (la commande tourne dans le conteneur qui lit la variable) |
| P5 | les slugs sans créateur sont exactement ceux du fichier ; aucun n'a d'origine ; aucun ne finit par l'identifiant d'un compte (la garantie du retour arrière, `sans-commun.md` § 5) |
| P6 | aucune référence orpheline (`recipe_row`, `shopping_list_row`, `shopping_list_ingredient`, `drive_choice`, `conversion`) |

**Empreinte des 261** : somme de contrôle de `(slug, name, slugged_name, image, department, default_cooking_unit, default_purchase_unit, compatible_units, adopted_from)` triée par slug, plus le nombre de conversions propres de chacun ; **identique avant et après** (seuls `creator` et, en phase 1, `is_base` changent). Les tables de lignes (recettes, listes, choix) ont les mêmes nombres, les mêmes sommes de quantités, les mêmes versions et, pour les listes, les mêmes statut et date d'envoi : calculés avant et après par `AdoptionSnapshotReader`.

**Contrôles SQL** : les blocs de `sans-commun.md` § 5 (`passation-controles-avant-sql`, `passation-controles-apres-sql`, `passation-retour-arriere-sql`) sont **ceux que le test exécute** (`CatalogHandoverDocumentedSqlTest`, sur le modèle d'`AdoptionDocumentedSqlTest` : lire le document, `preg_match` sur le marqueur, remplacer `:'owner'`, exécuter sur la base de test, comparer au résultat de la commande, et jouer le retour arrière puis rejouer la passation).

## Critères d'acceptation

(Jeu de test : un propriétaire avec une recette, une liste envoyée au drive et un choix du drive sur trois anciens communs ; deux comptes migrés ; un compte vide actif ; un compte en attente ; cinq communs classés par un double du port.)

- **À blanc.** Aucun `INSERT`, `UPDATE` ni `DELETE` n'est émis (capture) ; le rapport dit ce qui serait fait et si l'on est « prêt » ; code de sortie 0, ou 1 si une anomalie bloquante interdirait d'écrire.
- **Phase 1.** Les communs reçoivent le marqueur d'après le port (nombre de vrais et de faux exact) ; un commun hors fichier ou un commun du fichier absent : refus, rien n'est écrit.
- **Phase 2.** Le compte vide reçoit les ingrédients de base **et** ceux que ses lignes référencent, ses lignes sont repointées, empreintes identiques ; les comptes migrés et le propriétaire ne reçoivent rien (somme de contrôle de toutes les tables, versions comprises) ; le compte en attente n'est pas touché.
- **Préconditions.** Pour chacune de P1 à P6, un test où elle manque : `--apply` s'arrête avant la phase 4, **aucun** ingrédient n'a changé de créateur. En particulier : un compte actif non amorcé (P3), une ligne d'un autre compte sur un ingrédient sans créateur (P2), l'interrupteur coupé (P4).
- **Phase 4.** Les cinq anciens communs ont `creator` = le propriétaire ; **rien d'autre** n'a changé (somme de contrôle de toutes les tables hors `ingredient.creator`, versions des recettes et des listes comprises ; la liste envoyée garde statut et date d'envoi) ; le plan d'envoi et l'estimation du drive du propriétaire sont **identiques** (`GetDrivePlan`, `GetDriveEstimate`) ; le compteur « ingrédients créés » du propriétaire a augmenté de cinq, une fois.
- **Idempotence.** Un second `--apply` n'écrit aucune ligne et n'annonce rien ; `--check` répond « Rien à faire » (code 0).
- **Atomicité.** Une erreur injectée dans la phase 4 (déclencheur PostgreSQL) annule `UPDATE` et annonce ; un échec de la phase 2 pour un compte arrête la commande, les comptes déjà amorcés le restent.
- **Concurrence.** Une activation qui amorce un compte pendant la phase 4 réussit (la règle d'amorçage lit les deux formes) ; un compte activé entre P3 et la fin et non amorcé (interrupteur coupé) est détecté par la vérification de la phase 5.
- **Retour arrière.** Le SQL documenté, joué sur la base passée, remet « sans créateur » les seuls anciens communs (pas un ingrédient créé après), puis une nouvelle passation rétablit l'état.
- **Compatibilité** (ADR 0017 règle 6) : aucune migration dans ce ticket ; sur la base passée, le code **d'avant ce ticket** (image précédente, `deploy-smoke`) lit recettes, listes, plan d'envoi et ingrédients de l'administrateur et des comptes migrés.
- **Jeu de données de production** (reproduit en test) : 261 communs, 151 de base ; les sommes de contrôle du fichier sont celles du document.
- **Budget** : `passation-communs` (phase 4) figé, constant en nombre d'ingrédients.

`repas-dev` § 4 ; roadmap cochée ; `docs/production.md` ; PR « À relire » : le rapport à blanc d'un jeu reproduisant la production (nombres seulement), les requêtes SQL émises par phase, le temps mesuré. **L'agent n'exécute jamais le script ni la commande en production.**

## Pièges

- **L'ordre des phases est tout** : 1, 2, puis 3 et 4 dans la transaction. Une phase 4 qui précède l'amorçage rend le compte vide aveugle.
- Après un `UPDATE` en masse, vider l'identity map de Doctrine (`clear()`) avant toute relecture ; ne charger aucun agrégat dans la commande.
- **Le moteur de la phase 2 est celui d'ING-008** : ne pas en écrire un troisième.
- Ne pas modifier `recipe.version` ni `shopping_list.version` : rien n'est repointé pour le propriétaire.
- Ne pas afficher l'adresse du propriétaire ni un identifiant : la référence courte (8 caractères du SHA-256 de l'identifiant), comme ING-003. Dans les tests, une adresse de test, jamais celle de `User::PROTECTED_EMAIL`.
- Le fichier de classement est une **donnée de production validée** : ne jamais « corriger » un classement dans ce ticket ; une demande de changement passe par le propriétaire, puis le TSV et le JSON ensemble.
- La commande ne crée ni ne supprime aucun ingrédient : si un test le voit faire, c'est un défaut.
- Une sortie du back le jour de la passation est interdite (règle d'ING-003) ; la commande ne le sait pas, le script et le guide le disent.

## Réalisation (PR back #245)

Livré comme décrit ci-dessus, avec les écarts et ajouts suivants, tous décidés pour tenir l'intention du ticket et de l'amendement du 2026-10-20. **Aucune migration de schéma ; rien n'a été exécuté en production** : la commande et son script se lancent à la main, avec sauvegarde, à blanc d'abord (`sans-commun.md` § 14). Tout a été prouvé sur des bases jetables.

**Contrats** :

- **Données** : `src/Repas/Infrastructure/Data/base-ingredients.json` (261 lignes, même ordre que le TSV) ; port `Domain\Interface\BaseIngredientClassification::all(): array<string, bool>`, implémentation `Infrastructure\Catalog\BaseIngredientJsonClassification` (refuse un fichier incohérent), double `tests/Helper/BaseIngredientClassificationInMemory`. **`BaseIngredientsDataTest`** : 261 slugs uniques, 151 vrais, 110 faux, sommes de contrôle `a43e401aaf59b6e65bd1f433f7347c7b` et `3776a0ad5d1fbc427f9431656c14b7e2`, **JSON et TSV identiques ligne à ligne** (une seule source de vérité : le test échoue si l'un des deux bouge), aucun slug au format d'un compte.
- **Domaine** : port `IngredientCatalogHandoverRepository` (`lock`, `slugsWithoutCreator`, `state`, `classify`, `assignToOwner`, `fingerprint`), valeurs `CatalogHandoverState` et `HandoverPrecondition`, **service pur `CatalogHandoverPreconditions`** (P1 à P7, jugées sur un état lu : le même code sert la commande, qui les relit dans sa transaction, et le rapport), `IngredientCatalogException` (`classificationMismatch`, `preconditionsNotMet`, `handoverVerificationFailed`, sans identifiant).
- **Application** : commandes `ClassifyBaseIngredients` (phase 1) et `HandOverCatalog` (phase 4) ; requête `GetCatalogHandoverReport` + port `CatalogHandoverReportLoader` + `CatalogHandoverReportDTO`. L'amorçage (phase 2) est `SeedUserIngredientsCommand` d'ING-008 (`acceptSent` donné par `--accept-sent`).
- **Infrastructure** : `CatalogHandoverReader` (douze lectures, partagées par la commande et le rapport, comme `AdoptionSnapshotReader` et `SeedingSourceReader`), `IngredientCatalogHandoverPostgreSQLRepository`, `CatalogHandoverReportPostgreSQLLoader`, console `repas:ingredients:hand-over-catalog` (`src/Command/HandOverCatalogIngredientsCommand.php`, boucle et affichage seulement).
- **Exploitation** : `.claude/skills/repas-ops/references/passer-communs-a-l-administrateur.sh` (nom du ticket), `references/passation-ingredients.md` (pas à pas guidé), `docs/production.md` « Passation du catalogue », `sans-commun.md` §§ 5, 6 et 14 (relevés R1 à R6, procédure, retour arrière).

**La commande** : `php bin/console repas:ingredients:hand-over-catalog` ; sans option, **à blanc** ; `--check` ; `--apply` ; `--apply --stop-before-handover` ; `--accept-sent` ; `--source=<nom>`. Elle s'arrête au premier échec, refuse d'écrire hors `prod` et `dev`, est idempotente (un second `--apply` n'écrit rien et le dit). Détail : `sans-commun.md` § 6.

**Écarts avec le ticket** :

1. **P7 en plus** : « aucune ligne du propriétaire ne désigne l'ingrédient personnel d'un autre compte ». Sans elle, l'invariant d'après la passation (§ 5, contrôle 3) serait rouge sans que la passation y soit pour rien et la vérification de la phase 5 échouerait après l'écriture. Les six autres sont celles du ticket. **P2 est stricte** (une ligne sur un ingrédient **sans créateur**), pas `SeedingHealthDTO::foreignLines` (qui compte aussi une ligne sur l'ingrédient d'un autre compte) : seul le premier cas change avec la passation ; la vérification finale, elle, exige la requête de santé verte.
2. **À blanc, le rapport lit l'amorçage « comme si le classement était posé »** (`IngredientSeedingReportLoader::report(…, ?array $assumedBaseSlugs)`, `IngredientVisibility::isBaseCatalogSql(…, $assumedBaseParameter)`, `SeedingSourceReader::read(…, $assumedBaseSlugs)`, tous à `null` par défaut : l'écriture lit toujours la colonne) : sinon, avant la phase 1, le rapport de l'amorçage ne peut rien dire (« aucun ingrédient de base ») et l'on découvrirait une liste envoyée à repointer **après** la sauvegarde et le classement.
3. **Le code de sortie du mode à blanc dit si `--apply` avec les mêmes options écrirait (0) ou refuserait (1)**, et `--check` accepte `--stop-before-handover` : le script s'arrête avant la sauvegarde sur un refus, et ne sauvegarde pas quand il n'y a rien à faire.
4. **Aucune écriture à moitié quand le refus est prévisible** : `--apply` complet projette P2 et P3 (que l'amorçage lève) et juge les autres telles quelles ; s'il sait que la phase 4 sera refusée (P4 : l'interrupteur est coupé, par exemple), il n'écrit **rien**, ni classement ni amorçage. `--stop-before-handover` n'exige que l'absence d'anomalie bloquante et l'accord pour les listes envoyées.
5. **`--accept-sent` est un accord explicite** (comme `repas:ingredients:seed`), pas un `true` forcé : sans lui, une liste envoyée à repointer arrête tout avant la sauvegarde.
6. **Le retour arrière SQL du plan ramène aussi la statistique « ingrédients créés »** du propriétaire (une seule instruction avec `WITH … RETURNING`) : sans cela elle restait à +261 et une nouvelle passation la comptait deux fois. Le bloc `passation-retour-arriere-sql` de `sans-commun.md` a été modifié en conséquence ; testé : après lui, **toutes les tables sont identiques à ce qu'elles étaient juste avant la passation**, et rejouer la passation rétablit l'état d'après à l'identique.
7. **Deux corrections de performance dans `SeedingSourceReader` (code d'ING-008)**, découvertes en mesurant un propriétaire de 12 000 lignes : (a) la colonne « copie déjà présente » devient une table dérivée jointe une fois (la sous-requête corrélée relisait toute la table `ingredient` pour chaque candidat) ; (b) les trois `EXISTS` corrélés deviennent une sous-requête non corrélée : leur prix, multiplié par le nombre d'ingrédients, franchissait `jit_above_cost` et PostgreSQL compilait la requête (0,5 à 1 s pour 2 ms de travail). Même résultat (les 69 tests d'ING-008 passent), **1 s → 4 ms** par lecture ; l'activation d'un compte la lit deux fois, donc ce défaut aurait ajouté deux secondes (et plus avec les comptes) à chaque confirmation d'adresse en production. Règle ajoutée au skill `repas-dev` (§ 4).
8. Le nom du script et de la sauvegarde sont ceux du ticket et de `sans-commun.md` (`passer-communs-a-l-administrateur.sh`, `avant-passation-communs`).

**Ce qui est prouvé** (tout sur une vraie base de test, des sommes de contrôle calculées indépendamment du code testé, un jeu de données `HandoverDataset` de type production : les 261 vrais anciens communs du fichier dont une centaine de conversions propres, le propriétaire sans ingrédient personnel avec 15 recettes, des listes de tous les statuts dont **deux envoyées** et des choix du drive de deux enseignes, six comptes migrés avec leurs copies, alias et lignes repointées dont une collision de slug, le compte vide avec une liste envoyée, un compte en attente, un compte désactivé) :

- **à blanc** : aucun `INSERT`, `UPDATE` ni `DELETE`, aucun verrou (capture des requêtes) ; toutes les tables inchangées ;
- **phase 1** : 151 de base, 110 spécifiques, exactement le fichier ; un commun inconnu ou manquant est une anomalie bloquante et le cas d'usage refuse d'écrire ; un classement posé n'écrit plus rien ;
- **phase 2** : le compte vide reçoit les 151 et les 5 que ses lignes référencent, ses lignes sont repointées, contenu et listes envoyées inchangés (statut, date), versions +1 pour lui seul ; le propriétaire, les six comptes migrés, le compte en attente et le désactivé : strictement rien (copies, alias, lignes, versions, statistiques) ;
- **préconditions** : un test par précondition qui manque, deux fois : la commande complète s'arrête **avant toute écriture** (somme de contrôle de toutes les tables) en nommant la précondition, et le cas d'usage de la phase 4 appelé seul, qui les relit **dans sa transaction**, refuse sans changer un créateur ni annoncer la statistique ;
- **phase 4** : 261 anciens communs au propriétaire (mêmes sommes de contrôle, 151 de base, origine vide, mêmes conversions propres), **toutes les tables identiques sauf `ingredient.creator`** (somme de contrôle par table, versions des recettes et des listes comprises), le propriétaire intact (contenu, versions, listes envoyées avec statut et date, choix du drive et produits), les six comptes migrés, le compte vide et les deux autres comptes inchangés, la statistique « ingrédients créés » du propriétaire +261 **une fois**, **un seul `UPDATE` d'ingrédients et celui de la statistique, aucun `INSERT` ni `DELETE`** ; plan d'envoi et estimation du drive du propriétaire et d'un compte migré **identiques** avant et après, au slug près (`HandOverCatalogDriveEquivalenceTest`) ;
- **idempotence** : un second `--apply` n'écrit aucune requête d'écriture, n'annonce rien, toutes les tables inchangées ; `--check` répond « Rien à faire : passation faite et conforme » (0) ; un marqueur que le propriétaire change ensuite est respecté et n'est qu'une information ;
- **atomicité** : une faute dans la phase 4 (déclencheur PostgreSQL au centième ingrédient) annule l'`UPDATE` entier et la statistique ; une empreinte qui diverge (nom modifié pendant la passation) ou une version de recette qui monte annulent tout ; une faute dans l'amorçage du compte vide arrête la commande (le classement déjà posé le reste, le compte n'a rien reçu) ; un compte activé pendant la passation sans amorçage est vu par la vérification de la phase 5 ; une activation avant ou après la passation donne les mêmes 151 ingrédients ;

**Points d'attention pour la suite** :

- **Exécution** : suivre `sans-commun.md` § 14 ; le rapport à blanc répond « refuserait d'écrire » tant que P4 manque, même s'il peut déjà classer et amorcer (`--jusqu-a-l-amorcage` dit « écrirait »). Un compte en attente ou désactivé qui a des lignes sur un ancien commun bloque P2 : le servir un par un (`amorcer-ingredients.sh --compte=<référence>`).
- **ING-013 / ING-014** : la passation est le seul code qui lit `creator IS NULL` pour décider (`CatalogHandoverReader`, `IngredientCatalogHandoverPostgreSQLRepository`, `CatalogHandoverPreconditions`, `ClassifyBaseIngredientsHandler`) ; ils partent avec la commande et le fichier de classement une fois la passation contrôlée. `NoSharedIngredientTest` (ING-014) devra les exclure ou les retirer.

- **Retirer la commande après** : `repas:ingredients:hand-over-catalog` n'a plus de raison d'être une fois la passation faite et contrôlée ; ING-014 la retire avec `repas:ingredients:adopt-commons`.
